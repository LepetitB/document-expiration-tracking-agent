## Part A — Methodology (วิธีพัฒนาระบบ)

### A1. กระบวนการโดยรวม: Design → Build → Measure แบบวนรอบ

```
 ① เข้าใจปัญหา        ② ออกแบบ             ③ สร้างทีละชั้น         ④ ทดสอบ & วัดผล        ⑤ ปรับปรุง
 Rationale +      →   Problem→Solution  →  core → extraction  →   unit/e2e tests    →   แก้จากสิ่งที่
 Literature Review    + architecture        → agent → UI           + eval set + baseline   วัดได้ แล้ววนกลับ ③
```

| ขั้น | ทำอะไร | ผลผลิต |
|-----|-------|-------|
| ① Discover | วิเคราะห์ pain point, root causes, ค่าเสียหาย และสำรวจโซลูชันที่มีอยู่ | [01-rationale](01-rationale.md), [02-literature-review](02-literature-review.md) |
| ② Design | กำหนดเกณฑ์ C1–C8, เลือกแนวทาง hybrid, ออกแบบ pipeline / data model / agent tools | [03-proposed-solution](03-proposed-solution.md) |
| ③ Build | พัฒนาจากชั้นล่างขึ้นบน (ดู A3) โดยใช้ AI coding agent ช่วยเขียนโค้ด (โจทย์อนุญาต) | โค้ดใน `app/` (~1,400 บรรทัด Python, 9 หน้า template) |
| ④ Test & Measure | unit test ทุกกฎ, end-to-end test ผ่านเว็บ, ชุดเอกสารทดสอบพร้อมคำตอบที่ถูก, เทียบกับ baseline | `tests/`, `eval/evaluate.py`, `data/samples/` |
| ⑤ Iterate | แก้บั๊กที่ test และ eval จับได้ แล้ววัดซ้ำ | ดูหัวข้อ B4 |

### A2. หลักการออกแบบที่ใช้ (ทำไมสร้างแบบนี้)

| หลักการ | ทำอย่างไรในระบบ | เหตุผล |
|--------|----------------|-------|
| **ให้ AI ทำเฉพาะสิ่งที่ AI เก่ง** | LLM ทำหน้าที่ *อ่านและจำแนก* ส่วนการ *คำนวณวันที่ แปลง พ.ศ. และตัดสินสถานะ* ทำด้วยโค้ด | LLM อาจคำนวณตัวเลขพลาด แต่โค้ดให้ผลแน่นอนทุกครั้ง (deterministic) |
| **Structured output** | บังคับให้ LLM ตอบเป็น JSON ตาม schema (enum ประเภทเอกสาร, ฟิลด์ที่เป็น null ได้) | ไม่ต้อง parse ข้อความอิสระ และลด error |
| **Defense in depth** | กฎตรวจสอบ → confidence score → คนตรวจ | ไม่มีชั้นไหนสมบูรณ์ แต่หลายชั้นรวมกันลดความผิดพลาดที่หลุดไปได้ |
| **Human-in-the-loop** | ความมั่นใจต่ำกว่า 85% หรือผิดกฎข้อใด → เข้าคิว "ตรวจทาน" ก่อนเข้าระบบเตือน | ความผิดพลาดที่แพงที่สุดคือ "ผิดแต่ระบบเชื่อ" |
| **Grounded agent** | Agent ตอบจาก tool ที่ query DB จริงเท่านั้น (5 tools) | กัน Agent แต่งข้อมูลเอกสารขึ้นมาเอง |
| **Graceful degradation** | ไม่มี API key → ใช้ระบบกฎแทน, ไม่มีช่องทางแจ้งเตือน → เขียนลง outbox | ระบบยังใช้ได้เสมอ และใช้เป็น baseline ได้ |
| **Idempotent alerts** | บันทึก (เอกสาร, รอบเตือน) เป็น unique key | เตือนครบทุกรอบ แต่ไม่ส่งซ้ำ |

### A3. ลำดับการพัฒนา (Build order)

1. **Core rules:** `thai_date.py` (แปลงวันที่ไทย 10+ รูปแบบ), `status.py`, `validator.py` เขียน unit test ก่อน เพราะเป็นส่วนที่ต้องถูก 100%
2. **Storage:** SQLite schema (owners / documents / notifications) + ตรรกะ "ต่ออายุแล้ว" อัตโนมัติ
3. **Extraction:** 2 engine ที่คืนผลรูปแบบเดียวกัน คือ `claude` (Vision LLM) และ `rules` (ข้อความ PDF/TXT + regex) แล้วตามด้วยขั้น `normalise()` ร่วมกัน
4. **Notifier:** ตรวจรายวัน รอบ 90/60/30/7/0 วัน ส่ง Email / Discord / LINE / outbox
5. **Agent:** tool-use loop + โหมดออฟไลน์ที่ใช้ tools ชุดเดียวกัน
6. **Web UI:** Flask 6 หน้า (Dashboard, Upload, Review, Add, Chat, Alerts)
7. **Evaluation:** ชุดเอกสารสังเคราะห์ 7 ประเภท + ground truth + สคริปต์วัดผลรายฟิลด์

### A4. Tech stack และเหตุผล

| ส่วน | เลือก | เหตุผล |
|-----|------|-------|
| ภาษา | Python | มีไลบรารี AI และเอกสารครบ ทีมคุ้นเคย |
| AI | Claude API (`claude-opus-5-5`) — vision + structured outputs + tool use | อ่านภาพหรือ PDF ภาษาไทยได้โดยไม่ต้องเทรน, ส่ง JSON ตาม schema, ทำ agent ได้ในตัว และเปลี่ยนรุ่นได้ผ่าน `.env` |
| เว็บ | Flask + HTML/CSS | เบา และรันบนเครื่อง Windows ที่มี Smart App Control ได้ (ดู B4) |
| ฐานข้อมูล | SQLite | ไม่ต้องติดตั้ง server และย้ายไป PostgreSQL ได้ภายหลัง |
| ทดสอบ | pytest | unit + end-to-end ผ่าน Flask test client |

### A5. วิธีประเมินผล (Evaluation methodology)

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **ชุดข้อมูล** | เอกสารสังเคราะห์ 7 ฉบับ ครอบคลุม 7 ประเภท (ใบขับขี่, ภาษีรถ, พ.ร.บ., Work Permit, ประกันรถ, ใบอนุญาตประกอบการ, สัญญา) แต่ละฉบับมี 2 รูปแบบ: `.txt` (ข้อความ) และ `.png` (ภาพที่หมุนเอียงและเบลอเล็กน้อย จำลองการถ่ายด้วยมือถือ) |
| **ความยากที่ใส่ไว้** | ปี พ.ศ. 4 หลัก, ปี 2 หลัก (`26/11/69`), เลขไทย (`๑ ธ.ค. ๒๕๖๙`), วันที่ภาษาอังกฤษ (`31 Mar 2027`), หลายวันที่ในเอกสารเดียว (วันเกิด/วันออก/วันหมดอายุ), วันเริ่มและวันสิ้นสุดอยู่บรรทัดเดียวกัน |
| **Ground truth** | `data/samples/ground_truth.json` (ประเภท, เลขที่, วันหมดอายุแบบ ค.ศ., ผู้ถือหรือทะเบียน) |
| **Metrics** | (1) accuracy รายฟิลด์ (2) % ที่ถูกส่งให้คนตรวจ (3) **False-confident rate** = ผิดแต่ระบบยืนยันเอง (ตัวที่สำคัญที่สุด เป้าหมายคือ 0) |
| **Baseline** | engine `rules` (regex + keyword) เทียบกับ engine `claude` (Vision LLM) บนชุดเดียวกัน |
| **คำสั่ง** | `python -m eval.evaluate --engine rules --ext txt` / `--engine claude --ext png` (ผลบันทึกที่ `eval/results_*.md`) |
| **ทดสอบระบบ** | 30 automated tests: วันที่ไทย, สถานะ, กฎ validation, confidence, รอบแจ้งเตือน, ทุกหน้าเว็บ render ได้, อัปโหลด→ตรวจทาน→ยืนยัน, ต่ออายุแล้วฉบับเก่าเลิกเตือน, เตือนไม่ซ้ำ, Agent ตอบผ่าน tool |

### B3. อธิบายผล: เกิดอะไรขึ้น และหมายความว่าอะไร

0. **Claude Vision อ่านภาพถ่ายได้ถูก 100% ทุกฟิลด์ (28/28) และไม่ต้องให้คนตรวจเลย (0/7) ขณะที่ระบบกฎอ่านภาพได้ 0%** — ปิด root cause #1–3 ได้จริง: อ่านเลขไทย ปี 2 หลัก ภาษาอังกฤษ และแยกวันเกิด/วันออก/วันหมดอายุถูกทุกฉบับ ส่วนการแปลง พ.ศ.→ค.ศ. ทำโดยโค้ดของเราจากข้อความดิบที่ Claude คัดลอกมา
   - ภาษีรถ (ปี 2 หลัก `26/11/69`) ได้ความมั่นใจ 0.85 พอดีเส้น — แปลว่า Claude ประเมินความไม่แน่นอนของรูปแบบปีแบบย่อได้สมเหตุสมผล ถ้าต่ำกว่านี้นิดเดียวจะถูกส่งให้คนตรวจ
   - ⚠️ ชุดทดสอบเป็นภาพสังเคราะห์ที่ค่อนข้างชัด 7 ฉบับ ผล 100% จึง **ยังไม่ใช่หลักฐานว่าแม่นกับเอกสารจริงทุกแบบ** ต้องทดสอบกับภาพถ่ายจริงที่ยากกว่า (B6)

1. **ระบบกฎทำได้ 100% กับไฟล์ข้อความ แต่ 0% กับภาพถ่าย**
   - กฎ regex ใช้ได้ดีเมื่อมี "ข้อความ" อยู่แล้ว และรูปแบบอยู่ในขอบเขตที่เขียนกฎไว้ ทั้งเลขไทย, ปี 2 หลัก และวันที่ภาษาอังกฤษแปลงถูกทุกกรณี
   - แต่เอกสารจริงในหน้างานส่วนใหญ่มาเป็น **รูปถ่ายจาก LINE หรือสแกน** ซึ่งระบบกฎอ่านไม่ได้เลย
   - ตรงกับ root cause #1 ใน Rationale และเป็นเหตุผลที่ต้องใช้ Vision LLM
   - ⚠️ ผล 100% บน `.txt` เกิดจากชุดทดสอบที่สะอาดและทีมเขียนกฎเอง จึงไม่ได้แปลว่าระบบกฎจะแม่นกับเอกสารจริงที่หลากหลายกว่า

2. **False-confident = 0 ทุกกรณี: กลไกความปลอดภัยทำงานตามที่ออกแบบ**
   - เมื่อระบบไม่แน่ใจ (ความมั่นใจของระบบกฎถูกจำกัดไว้ที่ ≤ 0.8 และอ่านภาพไม่ได้จึงเป็น 0) เอกสาร **ทุกฉบับถูกส่งให้คนตรวจ** ไม่มีฉบับไหนผิดแล้วหลุดเข้าระบบเตือน
   - ต้นทุนของระบบกฎคือคนต้องตรวจ 7/7 ฉบับ ส่วน Claude **ลดเหลือ 0/7 โดย false-confident ยังเป็น 0** — ตรงตามเป้าหมาย

3. **การแปลงวันที่ทำด้วยโค้ด ไม่ใช่ LLM:** test ครอบคลุม 10 รูปแบบวันที่และผ่านทั้งหมด รวมถึงกรณีวันที่ไม่มีจริง (31 ก.พ.) ที่ระบบปฏิเสธอย่างถูกต้อง

### B4. ปัญหาที่พบระหว่างพัฒนาและวิธีแก้ (Lessons learned)

| ปัญหาที่พบ | พบจาก | วิธีแก้ | บทเรียน |
|-----------|------|--------|--------|
| Windows Smart App Control บล็อก DLL ของ `pyarrow` (Streamlit ต้องใช้) และ `jiter` เวอร์ชันล่าสุด | ติดตั้งแล้วรันไม่ได้ | เปลี่ยน UI จาก Streamlit เป็น Flask และ pin `jiter==0.11.1` | เครื่องผู้ใช้จริงมีข้อจำกัดด้านความปลอดภัย จึงควรเลือก dependency ที่เบา |
| วันที่ภาษาอังกฤษ (`31 Mar 2027`) ไม่ถูกตรวจจับ | eval รอบแรก expiry 6/7 | เพิ่ม pattern เดือนภาษาอังกฤษ | ชุด eval จับข้อผิดพลาดที่ไม่ได้คิดไว้ก่อน |
| "เริ่มต้น <วันที่> สิ้นสุด <วันที่>" อยู่บรรทัดเดียวกัน ทำให้ไม่ได้วันออก | ทดสอบอัปโหลดผ่านเว็บ | ถ้าบรรทัดมี 2 วันที่ ให้วันแรกเป็นวันออก | ต้องทดสอบด้วยข้อมูลหลายรูปแบบ |

### B5. ข้อจำกัดของผลลัพธ์ (ต้องพูดในวิดีโอ)
- ชุดทดสอบมีเพียง 7 ฉบับและเป็นข้อมูลสังเคราะห์ ควรเพิ่มเป็น 40–60 ฉบับและมีภาพถ่ายจริง (ปิดข้อมูลส่วนตัว)
- Claude Vision วัดบนภาพสังเคราะห์เท่านั้น ยังไม่ได้วัดกับภาพถ่ายเอกสารจริง (เบลอมาก มีเงา ถ่ายเอียงมาก)
- ยังไม่ได้วัด "เวลาที่ประหยัดได้" กับผู้ใช้จริง วิธีวัด: ให้คน 2–3 คนบันทึกเอกสาร 10 ฉบับ ด้วย Excel เทียบกับระบบนี้ แล้วจับเวลา

### B6. สิ่งที่จะทำต่อเพื่อเติมผลให้ครบ
1. เพิ่มเอกสารทดสอบที่ยากขึ้น เช่น ภาพถ่ายจริง (ปิดข้อมูลส่วนตัว), เบลอมาก, มีเงา, ปีผิดรูปแบบ, เอกสารไม่เกี่ยวข้อง — เพื่อดูว่า confidence + human review ยังกัน false-confident ได้ไหม

3. ทดสอบเวลาเทียบกับ Excel (user test)
